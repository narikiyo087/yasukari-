# 課題：レンタル延長の「記録」が残らない

- 発生の報告：2026-09-15（社長）「延長記録がマイページに表示されない（残らない）」
- 状態：**未対応。将来やるための記録**（このファイルは着手するときの起点）
- 対象：本番稼働中のヤスカリ（`yasukari-`）
- 関連：`docs/本番不具合_延長記録とログイン_調査.md`（ログイン問題と合わせた初回調査）

---

## 1. 何が起きているか

**記録が消えているのではなく、「延長した」という記録がそもそも作られていない。**

延長の決済が完了したときにしているのは、次の3つだけ
（`pages/mypage/rentals/extend/checkout/[reservationId].tsx`）。

1. Pay.JP で決済（`/api/payments/payjp`）
2. **予約レコードを上書き**（`PATCH /api/reservations/{id}`）
3. 延長完了メールを送る（`/api/reservations/extension/notify`）

2 で送っているのは次の4項目。**何日延ばしたか・いくら払ったか・いつ延長したかを表す行はどこにも作られない。**

| 項目 | どうなるか |
|---|---|
| `returnAt` | 延長後の返却日時で上書き（**延長前の返却日は消える**） |
| `paymentId` | **延長の課金IDで上書き** |
| `paymentDate` | **延長の決済日で上書き** |
| `extensionPaidFlag` | `true` にする |

3 のメール送信API（`pages/api/reservations/extension/notify.ts`）は**何も保存しない**。送るだけ。

---

## 2. その結果、マイページの表示が食い違う

マイページ（`pages/mypage/index.tsx`）が出しているのは次の3つ。

| 表示 | 出どころ | 延長後どうなるか |
|---|---|---|
| 利用期間 | `pickupAt` → `returnAt` | **返却日だけ伸びる**（ここは正しく変わる） |
| お支払い金額 | `paymentAmount` | **元の金額のまま。延長料金が加算されない** |
| お支払い日 | `paymentDate` | **延長の決済日に上書きされ、元の予約の決済日が消える** |

つまりお客様から見ると、**期間だけ伸びて、金額は元のまま、支払日だけ知らない日付に化ける。**
「延長した」という事実を示すものが画面に1つも無い。

`pages/mypage/rentals/[reservationId].tsx`（レンタル詳細）にも、延長を表示するコードは無い。

---

## 3. 見落とされやすい副作用（ここが一番痛い）

- **`paymentId` が延長の課金IDで上書きされる。**
  元の予約の Pay.JP 課金IDが失われるので、**元予約の返金・領収書の突き合わせができなくなる。**
- **2回目の延長は1回目を上書きする。** 履歴が無いので1回目は完全に消える。
- `extensionPaidFlag` は **true/false だけ**で、日数も金額も持たない。
  しかもこのフラグを読んでいるのは**管理画面だけ**（`pages/admin/dashboard/reservations/index.tsx:236`）。
  **マイページ側に延長を表示する実装は1行も無い。**

### いま延長の詳細が残っている場所

| 場所 | 残っているもの |
|---|---|
| お客様に届いた延長完了メール | 延長日数・前後の返却予定・料金（本文に記載） |
| `usermailHistory` テーブル | **メールを送った事実と日時だけ。**日数も金額も残らない |
| Pay.JP の決済履歴 | 金額と日時 |

→ 問い合わせが来るたびに**AWSとPay.JPを掘る**運用になっている。

---

## 4. 別件で見つけた事故（同じ場所を触るので一緒に直す）

`lib/reservations.ts` の `updateReservation()` は **`PutCommand`（項目まるごと置き換え）**で書いている。
書き込む中身は `reservationToRecord()` が組み立てたものだけ。
一方 `normalizeReservation()` は、**そこに含まれていないキーも読んでいる**。

**読むのに書かないキー＝更新のたびに DynamoDB から消える。**

- **`parking_number`（駐車位置）** … 実害あり。
  **延長したり、管理画面で予約を1か所直したりするだけで、その予約の駐車位置が消える。**
  セルフ店の受け取り案内に影響する。
- `thumbnail_url` / `store` / `pickup_datetime` / `return_datetime` / `id`（旧い別名キー）

---

## 5. 直し方（着手するときの案）

### A. 延長を「記録」として持つ（本命）

延長1回につき1行を残す。予約レコードに配列で持つか、別テーブルにするかは着手時に判断する。

```
RentalExtension
  extensionId / reservationId
  延長前の返却日時 / 延長後の返却日時 / 延長日数
  金額 / Pay.JP課金ID / 決済日時
  操作者（お客様本人 or スタッフ）
```

あわせて：

- 予約側の `paymentId` は**元の予約のものを保持**し、延長の課金IDはこの行に持たせる
- `paymentAmount` は「元の金額」と「延長ぶん」を分けて持ち、**合計は計算で出す**
- マイページの予約詳細に「延長の履歴」を出す（いつ・何日・いくら）
- `extensionPaidFlag` は**この行の有無から計算できる**ので要らなくなる

### B. `updateReservation` の項目消えを止める（小さい・先に単独で出せる）

- `reservationToRecord()` に `parking_number` を足す
- **読むキーと書くキーがずれていないかをテストで機械的に見張る。**
  ずれた瞬間に落ちるようにしないと、また別の項目で同じ事故が起きる

### C. 応急処置（Aを作るまでの間）

- **`paymentId` を上書きしない**
- **`paymentAmount` に延長ぶんを加算する**

この2点だけでも、表示の食い違いと返金時の実害は止まる。

---

## 6. 着手するときに先にやること

- **すでに延長されている予約は、元の課金IDと元の決済日がすでに失われている。**
  復元するなら Pay.JP の課金履歴から突き合わせる。対象の予約番号を先に洗い出す。
- 直す前に、いま残っている予約データを退避しておく。

---

## 7. 新システム（作り直し中のもの）への申し送り

`YASUKARI` リポジトリの `claude/design-m3-v2`（管理画面の作り直し）では、
**延長を「予約の上書き」ではなく「記録」として持つ。** ここでの失敗を繰り返さないため。
