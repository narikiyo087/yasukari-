# 本番実装前メモ（顧客連絡機能）

2026-08-14 時点。顧客連絡系機能（メール送信・通知・一斉配信）を本番公開する前に必ず対応・確認する項目をまとめる。

---

## 1.【必須】管理系APIへの認証追加

**現状、`/api/admin/` 配下のAPIには認証がかかっていない。**

Basic認証は `middleware.ts` で `/admin` 配下の**画面**にのみ適用されており、matcher が
`'/((?!api|wait).*)'` となっているため **`/api` 配下はすべて認証なしで到達できる**。
これは既存のテストメールAPIから続く構成で、今回追加した配信系APIも同じ構成に合わせている。

### 認証なしで叩けてしまう危険なAPI（影響が大きい順）

| エンドポイント | できてしまうこと |
|---|---|
| `POST /api/admin/broadcast` | 全会員へのメール・サイト内通知の一斉配信 |
| `POST /api/admin/newsletter-send` | メルマガの一斉配信・任意アドレスへのテスト配信 |
| `POST /api/admin/rental-reminders` | 前日リマインドの一括送信 |
| `POST /api/admin/test-mail` | 任意アドレスへのテストメール送信（既存） |
| `GET /api/admin/mail-history` | 送信履歴（顧客メールアドレス含む）の閲覧（既存） |
| `GET /api/admin/members` ほか members 系 | 会員情報の閲覧・更新（既存） |
| `POST /api/chatbot/inquiries/[sessionId]` | 問い合わせへの返信なりすまし（既存） |

### 推奨する対応（いずれか、上ほど推奨）

1. **管理APIに共有シークレットヘッダーを導入する**
   - 例: `ADMIN_API_KEY` を環境変数に持たせ、管理画面からの fetch に
     `x-admin-key` ヘッダーを付与し、API側ハンドラ冒頭で検証する。
   - 管理画面は Basic認証の内側にあるため、ヘッダー値をページに埋め込んでも
     Basic認証を突破されない限り漏れない。
   - 実装箇所: 上記表のAPI全ハンドラ ＋ 各管理画面の fetch 呼び出し。
2. **middleware の matcher を変更して `/api/admin` にもBasic認証をかける**
   - matcher から `api` の除外を外し、`/api/admin` 配下に `requireBasicAuth` を適用。
   - 注意: ブラウザのBasic認証資格情報は `/admin` 配下で認証した場合、
     `/api` へのfetchには自動付与されないため、管理画面側で
     `Authorization` ヘッダーを明示的に付ける改修が併せて必要になる。
3. Cognitoの管理者ロール（`custom:role`）による認可に統一する（工数大・将来課題）。

> 上記に加えて `manual_for_system` 同様、admin画面のBasic認証の
> 初期パスワード（`lib/basicAuth.ts` のデフォルト値）を本番では必ず環境変数で上書きすること。

## 2.【必須】SMTP設定

メール送信は SMTP 一本（nodemailer）。以下を本番環境変数に設定すれば全メールが実送信になる。

```
SMTP_HOST / SMTP_PORT / SMTP_USER / SMTP_PASS / MAIL_FROM
```

- 未設定の間は全経路で「送信スキップ＋メール履歴に skipped 記録＋サイト内通知のみ」で動作する（デモ用の安全動作）。
- Xserver等のSMTPを使う場合は時間あたりの送信数上限に注意。
  アプリ側のレート制御（毎秒5通・同一宛先10秒間隔・3連続失敗で宛先ブロック）は `lib/mailQueue.ts` に実装済み。

## 3.【推奨】前日リマインドの自動実行

管理画面（レンタル前日リマインド）から手動一括送信できるが、本番では毎日の自動実行を推奨。

- `POST /api/admin/rental-reminders` を **EventBridge Scheduler 等で1日1回**（例: JST 18:00）叩くだけでよい。
- 送信済み予約はサイト内通知の履歴で自動スキップされるため、多重実行しても重複送信はされない。
- ※ 1. の認証を導入したら、スケジューラ側にも同じ認証ヘッダーを付けること。

## 4. 運用上の注意

- **メルマガ配信はオプトイン制**：通知設定で「メルマガ・クーポン」をオンにした会員のみが本配信の対象。
  初期値はオフのため、運用開始直後は対象0名になり得る（仕様どおり）。
- **全体通知**は「全体通知」をオフにした会員を除外して配信される。
- **メール通知オフ**の会員には、一斉配信・リマインドはサイト内通知のみ届く。
  仮登録・本登録・予約完了などのトランザクションメールは設定に関わらず送信される（意図した挙動）。
- 一斉配信は会員テーブル・Cognitoの全件取得＋会員ごとの設定取得を行うため、
  会員数が数千名規模になったら配信処理の非同期化（キュー化）を検討する。

## 5. コスト（AWS課金）

- メール送信自体はSMTP経由のため **AWS課金には影響しない**。
- AWSに載るのはメール1通あたり DynamoDB 書き込み2回（送信履歴＋サイト内通知）のみ。
  オンデマンド課金で100万書き込み約200円 → 月数千通規模なら実質0円。
- SESへ移行する場合は1,000通あたり約$0.10。

## 6. 未実装・既知の課題

- **英語版マイページのレンタル延長画面が未実装**。EN利用者には延長完了メールのトリガーが存在しない。
  延長導線をENにも用意する場合は `pages/mypage/rentals/extend/` の移植が必要。
- キーボックス関連の既存テスト3件（`__tests__/keybox.test.ts`）が失敗中。顧客連絡系とは無関係の既存問題。
- 開発環境ではNext.jsのAPIルートごとにモジュールが分かれるため、DynamoDB未接続時の
  インメモリのメール履歴が `mail-history` 画面に表示されないことがある（本番はDynamoDBに記録されるため問題なし）。
