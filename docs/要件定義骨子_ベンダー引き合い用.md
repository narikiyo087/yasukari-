## 3. エリア拡大にあたって新たに設計が必要な論点

### 3.1 店舗マスタの新設 【最重要】

- **現状（A）**：店舗が「足立小台本店」「三ノ輪店」という**文字列としてコード内に散在**しています。予約レコードは店舗名を文字列で直接保持しており、店舗を増やす構造になっていません。休業日カレンダーのみ店舗 ID をキーに持つ、部分的な対応にとどまります。
- **必要（B）**：店舗マスタを新設し、店舗ごとに以下を持たせる必要があります。
  - 営業時間・休業日・**有人／無人セルフの別**
  - 在庫（配置車両）
  - スマートロックのユニット設定
  - 駐車区画の管理
- 店舗の追加が**運用担当者の画面操作だけで完結する**ことを要件にすべきと考えています（要検証）。

### 3.2 GPS／テレマティクスの搭載 【未着手】

- **現状（A）**：モックアップに GPS 関連の実装は一切ありません。完全な新規領域です。
- **未確定（C）**：導入目的が確定していないため、以下を要件定義の初期に決める必要があります。
  - **目的**：盗難対策 ／ 返却判定の自動化 ／ 無断延長の検知 ／ 稼働率の分析 — どれを主目的とするか（測位頻度と通信コストが桁で変わります）
  - **給電方式**：車両電源（12V）直結か、内蔵バッテリー式か。レンタル車両は入れ替えがあるため、設置・撤去の運用コストに直結します
  - **通信費**：SIM 月額 × 台数 × 期間。補助対象になりにくいランニングコストのため、事業計画の収支に影響します
  - **既存スマートロックとの統合**：位置情報と施解錠を**1つの管理画面で扱う**ことを要件とするか
- **補足（B）**：無人セルフ店を主力に据える方針であれば、対面での本人確認・車両確認が入らない分、**盗難対策と無断延長の検知**の優先度が上がると考えています。目的の順位付けの検討材料としてください。

### 3.3 乗り捨て（ワンウェイ返却）— スコープ外 【確定・A】

- **決定**：乗り捨ては**行いません**。借りた店舗に返却する運用を、多拠点化後も維持します。
- **意味**：在庫管理が各拠点内で閉じるため、拠点間の車両回送・在庫再配置・片道料金の設計が不要になります。多拠点システムとしては最も複雑度の高い部分が落ちるため、**見積のブレを抑えられる論点**です。
- 現行の利用規約・FAQ に既に明記されている運用と一致します。

### 3.4 車両マスタの再設計

- **現状（A）**：車両の識別子が `管理番号` `車両コード` `ナンバープレート` `駐車番号` と複数系統で混在しています。
- **必要（B）**：車両個体を一意に管理し、拠点間の移動履歴・整備履歴・GPS 機器の紐付けを追跡できる構造への再設計が必要と考えています。

### 3.5 スケーラビリティ

- **現状（A・技術的事実）**：DynamoDB のテーブル全件スキャンに依存した実装が 10 モジュールに存在します。モックアップとしては問題ありませんが、**拠点数・車両数・予約件数が増えると性能とコストの両面で破綻します**。本番実装では設計し直す前提です。

### 3.6 予約ステータスの体系化

- **現状（A）**：ステータスが日本語の自由文字列に近い形で扱われています。
- **必要（B）**：拠点・担当者が増えることを前提に、状態遷移を明確に定義し直す必要があります。

### 3.7 無人セルフ運用の可用性 【非機能要件】

- **前提（B）**：セルフ24時間店を主力に据える方針から、新規拠点も無人セルフを標準とする可能性が高いと考えています（要確認）。
- **論点**：無人店ではスマートロックの PIN／QR 発行が止まると**店舗が営業できなくなります**。有人店なら人が対応できますが、無人店では代替手段がありません。
  - スマートロック API 障害時のフォールバック手段
  - 深夜・早朝の障害検知と通知（誰が気づき、誰が対応するか）
  - 目標稼働率と、それを満たすための構成
- 無人セルフを主力にするほど、この非機能要件の重みが増します。**要件定義で明示的に扱っていただきたい領域**です。

## 4. ブランディング — 訴求の再配置

### 4.1 決定した方針 【A】

| 順位 | 訴求 |
|---|---|
| **1番目** | **セルフ24時間で借りられること** |
| **2番目** | **安いこと** |

現状は「安さ」が第一訴求です。これを入れ替えます。

### 4.2 現状とのギャップ 【A・検証済み】

モックアップと広告素材を確認したところ、現状は**方針と逆の構成**になっています。

1. **「格安」「激安」が主語になっている箇所が 13 ファイルに分布**しています。ページタイトル、meta description、SEO キーワード、屋号表記（「屋号：激安レンタルバイク ヤスカリ」）まで一貫して安さが先頭にあります。
2. **セルフ・24時間の記述は、三ノ輪店の説明の中にしか登場しません。** しかもトーンが注意書きです（「三ノ輪店は無人セルフ店舗のため、店員のサポートが受けられません」「セルフでのレンタルが難しそうな方は」）。**第一に推したいものが、現状は弱点として書かれています。**
3. **SNS 広告動画（30秒・3バリアント）の構成にセルフ24時間が入っていません。** 「選ばれる理由」として挙げている4点は「ネット予約完結／手ぶらOK／選べる車種／補償プランあり」で、価格訴求が 9〜16秒の中心に置かれています。

### 4.3 ベンダーに期待する作業範囲 【C】

上記を踏まえ、以下を一緒に整理していただきたいと考えています。

- 「セルフ24時間」を第一訴求に置いたときの、**サービスの言語化**（24時間いつでも／無人で完結／待たない、のどれを軸にするか）
- セルフを**不安要素ではなく利点として見せる** UI・導線の設計。予約フローの中でセルフ受渡の流れが自然に理解できることが要件になります
- サイト全体のコピー・タイトル・meta の書き換え方針（SEO への影響を含む）
- 広告素材の再構成方針
- 訪日外国人向けにどう見せるか（セルフ・非対面は言語障壁の低さという利点にもなり得ます）

ブランドの方向性が固まらないまま UI を実装すると後戻りが発生するため、**要件定義と並行して進めたい領域**です。

作成者が現時点で答えを持っていない項目です。ベンダー選定後、最初のヒアリングで確定させる想定です。

- [ ] セルフ店と有人店で**料金・サービス内容に差を設けるか**
- [ ] 現在の**業務フロー**（受付・引渡・返却・整備・保険対応）の実際
- [ ] 既存の会計・在庫・顧客管理ツールの有無と、**連携の要否**
- [ ] 保険・補償商品の設計（現状は車両補償・盗難補償の2種）
- [ ] **インバウンド利用比率**の実績と目標
- [ ] 現行サイト（本番）の状況と、**新システムへの移行方針**（データ移行の有無）
- [ ] 運用体制（システムを日々操作するのは誰か、IT リテラシー、深夜障害時の対応者）
- [ ] **予算の内訳イメージ**（ハード／ソフト／初期／ランニング）
- [ ] 稼働希望時期と、補助金の交付決定時期との整合

## 7. ご照会させていただきたい事項（RFI 項目）

8. 想定される**技術スタック**と、KJET 側での将来的な内製・引き継ぎの可否
